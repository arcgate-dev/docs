This tutorial has not yet been run end to end: this repo has no Web3Auth client id or Custom JWT connection configured yet. The code typechecks and fails fast with a clear error when its env vars are unset (shown below, for real); everything past that point is the expected shape, clearly labeled, until someone runs it against a real Web3Auth project.

This tutorial builds an agent that logs into a MetaMask Embedded Wallet (@web3auth/node-sdk v6, the SDK's own name for what used to be Web3Auth) with a JWT it mints itself, then pays arcgate over x402 and trades. The code lives in examples/metamask-trade/; this page walks through it.

What you'll build

Same chain split as tutorial 1:

  • Payment happens over x402 on Arc testnet (chain 5042002).
  • Execution - the transactions /trade/v1/swap hands back - targets Arc mainnet (chain 5042; locally, an arc-anvil fork of it).

The difference from tutorial 1: @web3auth/node-sdk's connect() reconstructs a real private key in this process and hands it back as a plain viem Account (privateKeyToAccount, wrapped in a WalletClient - see dist/lib.esm/Web3Auth.js's getWallet). That account can sign for any EVM chain, so this example runs the same account through both the testnet x402 payment and the mainnet-fork swap - no second wallet, no impersonation.

Before you start

  • Node 24 and pnpm. From the repo root: pnpm localnet (below) reads its x402 config from the root .env (apps/api/src/x402.ts), which ships with X402_ENABLED=false - create the root .env and turn it on before running it: FACILITATOR_URL: the default is Circle's hosted Facilitator Service; facilitator.arcusnetwork.co is a free third-party fallback that settles Arc testnet (eip155:5042002) - checked live against its /supported endpoint (see tutorial 1 for the check and a second fallback that doesn't). Then: pnpm localnet starts the API at your API_URL (localnet default http://127.0.0.1:19800) and an arc-anvil fork of Arc mainnet at your ARC_FORK_URL (localnet default http://127.0.0.1:19845) from compose.yaml. PAY_TO is who the API charges every paid call to; this example reuses it as ARCGATE_PAY_TO. Against a remote API instead, read payTo from a 402's PAYMENT-REQUIRED header without paying (see the ARCGATE_PAY_TO entry in examples/metamask-trade/README.md).
  • A MetaMask Embedded Wallets developer account (label may differ; the dashboard is also reachable from docs.metamask.io).
  • Prices: search 0.005 USDC, quote 0.01 USDC, swap 0.01 USDC, and - because the default Permit2 approval can need a second swap call - that second call is priced on its own too (see the prices table). Quotes live 120 seconds.

Note

@web3auth/node-sdk depends on @segment/analytics-node and sends SDK lifecycle events (init/connect started, completed, failed - clientId, network, team id, auth connection id, durations, error codes; not the idToken or the key) to a Segment write key hardcoded in the SDK. Reading dist/lib.esm/analytics.js: isSkipped() returns true unless NODE_ENV === "production", so nothing is sent when running this example locally (NODE_ENV is unset). There is no public option on Web3Auth to disable it independent of NODE_ENV; SegmentAnalytics has a private disable() the SDK never exposes.

1Set up Web3Auth

Create a project, pick the Sapphire Devnet environment (matches WEB3AUTH_NETWORK=sapphire_devnet, the default), and set up a Custom JWT connection. Steps as documented at docs.metamask.io/embedded-wallets/authentication/custom-connections/custom-jwt (label may differ where noted):

  1. Visit the Embedded Wallets dashboard and create a project. Choose environment Sapphire Devnet. Pick whichever project platform fits closest (label may differ for a headless Node client - Web is the closest fit).
  2. Copy the Client ID -> WEB3AUTH_CLIENT_ID.
  3. Chains are code-only for this example (see step 3): Web3Auth.init() merges chains passed in code with anything configured on the dashboard, code entries take precedence (initChainsConfig in dist/lib.esm/Web3Auth.js), so you do not need to add Arc testnet on the dashboard. You can anyway, under Chains & Networks > Add a Custom Network, if you want it listed there too.
  4. Go to Custom Connections. Click the Settings icon near Custom Connection.
  5. Enter an Auth Connection ID (anything stable, e.g. arcgate-metamask-trade) -> WEB3AUTH_AUTH_CONNECTION_ID.
  6. Paste the JWKS Endpoint: the URL where you'll host the JSON pnpm --filter @arcgate/example-metamask-trade jwks prints (see step 2).
  7. Paste a sample JWT to auto-populate validations, or configure manually.
  8. Select JWT user identifier: sub. Toggle case sensitivity if you need it.
  9. Click Add Custom Validations to add iss (-> WEB3AUTH_JWT_ISSUER) and, if you want one, aud (-> WEB3AUTH_JWT_AUDIENCE).
  10. Click Add Connection.

2Mint the agent's JWT

Generates an RS256 key pair, writes the PRIVATE key to ~/.arcgate/metamask-trade-jwt-key.pem (mode 0600, refuses to overwrite an existing file), and prints ONLY the public JWKS JSON:

Host that JSON somewhere reachable over HTTPS (a gist, a static file host, anything) and paste the URL as the JWKS Endpoint in step 1. Set WEB3AUTH_JWT_KID to the printed kid and WEB3AUTH_JWT_PRIVATE_KEY to the PEM's contents (\n for newlines is fine if you paste it on one line).

Never log this

The private key file never leaves your machine and is never printed. WEB3AUTH_JWT_PRIVATE_KEY signs every JWT this agent presents: never log it, never put it in an error message directly - reportFatal in src/main.ts passes both its raw form (whichever way you set it: real newlines or \n-escaped) and its newline-normalized form to @arcgate/wallets's redact (packages/wallets/src/redact.ts) before printing any error, so even a viem error that happened to quote it comes out blanked.

3Connect

No userId in LoginParams. Source-verified in getUserId (dist/lib.esm/Web3Auth.js): when loginParams.userId is set, it is returned as-is - there is no check that it agrees with the idToken's sub. Omitted, getUserId falls through to the idToken itself, getUserId(payload, ..., userIdField), deriving the id from sub - the Custom Connection's "JWT user identifier" field, set to sub in step 1. WEB3AUTH_USER_ID is still useful: it's the JWT's sub (step 2), so it's what the SDK ends up deriving as the user id, just not by being asserted against it.

connect() returns { chainNamespace, provider, signer }. This example refuses anything except chainNamespace === "eip155", then checks signer.account.type === "local" before using it: getWallet (same file) always builds the eip155 result with privateKeyToAccount + createWalletClient - a REAL local account, never a JSON-RPC-provider-backed one - so that check should always pass; it exists so a future SDK change would fail loudly here instead of silently somewhere later.

Never log this

provider.request({ method: "private_key" }) returns the raw private key as a hex string, when reachable at all - CommonPrivateKeyProvider's getPrivKeyMiddleware (in @web3auth/no-modal) refuses it unless the dashboard's Key Export setting is on. This example never calls it and never logs provider or walletClient.account beyond .address.

4Fund

Two different fundings, on two different chains:

  • Testnet USDC, for the x402 payments in the next step: send some to the connected address at faucet.circle.com (select Arc Testnet). This example's preflight step checks the balance first and points back here if it's short.
  • Native balance on the fork, for gas: src/fork.ts's fund() calls @arcgate/wallets's shared fundOnFork (packages/wallets/src/fork.ts, an anvil_setBalance call) for the same address, using the same formula as apps/smoke/src/run.ts's swap steps (3x the trade amount plus headroom). Nothing to do here by hand; it runs automatically before the swap.

5Pay x402 with the wallet

createViemSigner (packages/wallets/src/viem.ts) wraps ANY viem WalletClient with an Account - this one included - as an x402 signer, with the same guards as tutorial 1's Circle bridge: domain.chainId must be Arc testnet (5042002), domain.verifyingContract the testnet USDC contract, primaryType TransferWithAuthorization, message.from the wallet's own address, message.validBefore at most 900 seconds out. After signing, the recovered signer is checked against the address too.

testnetOnlyPolicy gates the same things one level up as an x402 client policy - see tutorial 1's step 4 for the full list.

6Search

This example buys TEN. Every quote executes through ArcgateRouter's executeGraph; whether the default Permit2 approval returns a permit to sign depends on the live route and allowance at swap time: if the route is funded with native USDC, or an existing Permit2 allowance to ArcgateRouter already covers the amount, the response comes back with signatures: [] and there is nothing to sign (see step 8); otherwise round 1 returns a Permit2 PermitSingle. The example handles both cases.

A search result's own verdict says whether it's safe to buy, not just whether it matched: the response's resolution (verified/clear_leader/single/ambiguous/none) says whether the query resolved at all, and each result's verification.status and flags say whether that specific candidate impersonates another token, has a lookalike symbol, can't be sold, or still has its safety verdict pending. pickSearchResult (packages/wallets/src/trade.ts, see tutorial 1's search step and the API reference) reads that verdict instead of taking the first same-symbol hit, and refuses instead of guessing when the query is ambiguous or the top result is flagged.

This example searches by address, not by ticker. TEN alone is an ambiguous ticker on Arc: a "TEN" search comes back resolution: "ambiguous" (several same-symbol tokens, each flagged ambiguous_ticker), and pickSearchResult refuses to guess. When the ticker is ambiguous, get the address from whoever gave the order and search by it: the answer is resolution: "single", match: "address", with the token's own flags still attached.

7Quote

The clock starts here: both swap calls in the next two steps, plus mining the approve transaction, need to land inside the 120-second expiresAt window, or the second call comes back 410 (see When things go wrong).

8Swap with Permit2

approval: "permit2" is the default, and the one this example runs for real (unlike tutorial 1's local executor, which had to fall back to "approve" - see its step 7). When a signature is needed (the route isn't funded with native USDC, and no Permit2 allowance to ArcgateRouter already covers the amount), round 1 returns a Permit2 PermitSingle to sign (signatures[0].typedData) and any approve transactions, built without the permit yet attached.

That shape (an approve tx plus a swap tx, and a permit to sign) holds on a first run for this wallet. Once the unlimited ERC-20 approve to Permit2 has landed on chain, a re-run reuses that allowance (packages/core/src/swap/approvals.ts's planApprovals) and comes back swap: 1 transaction(s), signatures=1 instead: only the swap tx, no approve.

9Sign and send

This example signs the permit before sending any approve transaction, and checks every plain transaction with assertSwapTransactions before sending it. /trade/v1/swap's own re-check does verify the client-sent message fields and the signature over them - what it can't do is protect this example from a buggy or compromised server, since it re-derives the typed data (and the transactions) it expects from the quote/route it itself produced, not from what was actually signed or sent. The wallet-side guards - signPermit2WithViem's permit check and assertSwapTransactions, both checked against this run's own config - are what do that.

signPermit2WithViem (packages/wallets/src/viem.ts) checks the permit's domain is Permit2 on Arc mainnet (5042) and primaryType is PermitSingle before signing - the same kind of refusal as step 5, guarding the mainnet-facing signature instead of the testnet one. The Permit2Context (packages/wallets/src/guards.ts) goes further than the domain check: spender must be the ArcgateRouter address this example got from its own config (env.arcgateRouter, never a value read back from the server), token must be the quote's sell token, and message.details.amount must not exceed maxAmount, the amount this run chose to sell (never a value read back from the server; a quote whose amountIn differs is refused before signing, hoisted to right after the quote - see step 7). A permit asking to move more than you chose to sell, or naming the wrong spender, is refused, not signed.

assertSwapTransactions (same file) checks the plain transactions /trade/v1/swap hands back, called on firstSwap.transactions right after step 8 and again on finalSwap.transactions here, both against the same txCtx built from this run's own config: an approve tx's to must be the sell token (canonicalized the same way as the swap tx's tokenIn below) and its calldata must decode to approve(spender, amount) with spender Permit2 (this example always uses the default permit2 approval mode). Exactly one swap tx is allowed: its to must be env.arcgateRouter, never a value read from the response, and its calldata must decode against ArcgateRouter's executeGraph ABI (any other selector is refused) to recipient === address and tokenOut === buyToken (this run's own config, never the response), amountIn within maxAmount, and minOut both positive and no looser than the floor (quote.best.minAmountOut) this run accepted at quote time (txCtx.minOut); its value must be 0 unless this run allows a native-USDC input, and then it must equal the decoded amountIn scaled to 18dp exactly (a native-USDC-funded swap's value uses native-token decimals, not USDC's 6). A buggy or compromised server returning approve(attacker, MAX), a swap to somewhere other than ArcgateRouter, or a swap whose TOP-LEVEL recipient/tokenIn/amountIn/tokenOut/minOut don't match, is refused here, before fork.send ever runs. This does not decode executeGraph()'s steps, pull, or deadline: a malicious server could still route the input badly inside steps while every top-level field above stays honest. That loss is bounded, not eliminated - ArcgateRouter only ever pays the checked recipient at least the checked minOut (_payGraphOutput, contracts/src/ArcgateRouter.sol), so the worst case is the same slippage this run already accepted at quote time. A server that lies consistently in both the quote and the swap is a bad-price problem no wallet-side structural check catches without an independent price source.

If signatures comes back empty (the route is funded with native USDC, or an existing Permit2 allowance to ArcgateRouter already covers the amount - see step 6), this example logs why plainly and sends the returned transactions - approves, then swap - without ever calling signPermit2WithViem. assertSwapTransactions still ran, right after step 8, on that same response.

The second swap call is a second paid x402 call, priced on its own. Any approve transactions from round 1 (sent above, before the round-2 call, each receipt checked for a revert), then the round-2 swap transaction, go on the fork with src/fork.ts's send(), a thin wrapper over @arcgate/wallets's shared waitForForkReceipt (packages/wallets/src/fork.ts):

account here is walletClient.account from step 3 - the SAME local account the SDK returned, reused as-is for a second WalletClient pointed at the fork's chain id (5042) and RPC. No chain switching through the SDK, no second wallet: a local viem account can sign for any chain by construction, so the only thing that needs to change between testnet payment and mainnet-fork execution is which WalletClient/chain it's plugged into.

When things go wrong

Same three failure shapes as tutorial 1, adapted, plus what's specific to a Custom JWT login.

402 loop from an unfunded wallet. A connected address with no testnet USDC signs a valid payment payload, but the facilitator refuses to settle it - the client gets a second 402 instead of a 200. Same mechanic as tutorial 1.

Expired quote (410). Calling swap past expiresAt - including the second, permit-attached call - never charges: no PAYMENT-RESPONSE header, settlement is null, body {"error":{"code":"quote_expired",...}}. The two-call Permit2 flow makes this easier to hit than tutorial 1's single call: mining the approve transaction on a busy fork can eat into the 120-second window.

Slippage revert. Needs a real price move between quote and execution to reproduce; not faked here. The swap transaction's receipt reverts on chain even though /trade/v1/swap's own re-simulation passed. The fix is to re-quote and swap again, never to relax minAmountOut.

Bad clientId or network. Web3Auth.init() calls fetchProjectConfig first; a wrong WEB3AUTH_CLIENT_ID or WEB3AUTH_NETWORK fails there with WalletInitializationError.notReady (code 5003, message includes "failed to fetch project configurations") - source-verified in dist/lib.esm/Web3Auth.js, before any login attempt.

Wrong authConnectionId or an unreachable JWKS endpoint. getOAuthProviderConfig doesn't fail on an unknown authConnectionId - it silently falls back to a default config. The failure surfaces one level down, in Torus's retrieveShares, straight from @toruslabs/torus.js's source:

An unreachable JWKS endpoint fails validation on the Torus nodes' side during the same call; this example has not reproduced the exact message live, so treat any retrieveShares failure around login as "check the Auth Connection ID and the JWKS Endpoint" first.

MFA already enabled on this user. connect() throws WalletLoginError.mfaEnabled() (code 5115) if the account already has MFA from elsewhere - this Node SDK doesn't support the MFA flow; use @web3auth/web3auth-web instead for that user.

Guard refusals. A refusing to sign error from assertX402Authorization or assertPermit2TypedData means the payload asked for something outside what this wallet is allowed to sign. A refusing to send error from assertSwapTransactions means a plain transaction asked for something outside what this run is allowed to send. Same as tutorial 1: a refusal by design, not a bug to work around.
