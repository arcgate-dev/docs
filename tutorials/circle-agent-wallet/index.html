This tutorial builds an agent that pays arcgate over x402 and trades with a Circle Developer-Controlled Wallet (DCW). The code lives in examples/circle-trade/; this page walks through it.

What you'll build

arcgate splits payment from execution onto two different chains:

  • Payment happens over x402 on Arc testnet (chain 5042002): every paid call - search, quote, swap - is settled there in USDC.
  • Execution - the transactions /trade/v1/swap hands back - targets Arc mainnet (chain 5042).

Locally, "Arc mainnet" is a arc-anvil fork of the real chain, so the swap never touches real funds. In production it's the real Arc mainnet.

This example uses two separate Circle wallets, in two separate wallet sets, under two separate API keys:

  • The payer: an ARC-TESTNET wallet, created with a Circle TEST key, that signs and pays x402. This is the only wallet this tutorial actually creates and funds.
  • The swap wallet: for production execution only, a LIVE-key ARC (mainnet) wallet with its own address, in its own wallet set. Circle TEST keys never reach mainnet, so this can't be the same wallet, key, or wallet set as the payer.

Locally, the fork executor impersonates the payer's address as a stand-in taker/recipient on the arc-anvil fork - arcgate allows taker/recipient to differ from the x402 payer, and the fork is local, so this is a safe stand-in for a real swap wallet. See Going to production for the real split.

4Pay x402 with the wallet (guards)

@arcgate/wallets' createCircleSigner wraps the Circle client as an x402 signer (packages/wallets/src/circle.ts). Before it signs anything, it checks:

  • domain.chainId is Arc testnet (5042002), never mainnet.
  • domain.verifyingContract is the testnet USDC contract.
  • primaryType is TransferWithAuthorization (EIP-3009) - not a Permit2 permit.
  • message.from is the wallet's own address.
  • message.validBefore is at most 900 seconds from now, even if the server offered longer.

After Circle signs, the recovered signer is checked against the wallet address too (assertSignedBy) - a self-check that catches a bad v byte instead of broadcasting a transaction that would never verify.

testnetOnlyPolicy (packages/wallets/src/x402.ts) gates the same things one level up, as an x402 client policy: scheme exact, network eip155:5042002, the testnet USDC asset, payTo matching ARCGATE_PAY_TO, an amount at or under ARCGATE_MAX_PAYMENT, and maxTimeoutSeconds under a cap. Neither check ever substitutes a different offer - an empty result means refuse, not fall back.

The same file also guards the Permit2 permit a mainnet swap can ask for (assertPermit2TypedData, step 8) - not just its chain and contract, but every field that decides what it actually authorizes: spender must equal the ArcgateRouter address the caller configured (Permit2Context.spender - obtained from this example's own config, never from the server response), details.token must match the quote's sell token, and details.amount must not exceed the amount this run chose to sell, and both sigDeadline and details.expiration are bounded. /trade/v1/swap's own re-check does verify the client-sent message fields and the signature over them - what it can't do is protect this example from a buggy or compromised server, since it checks the permit against the quote/route it itself produced. This wallet-side guard, checked against the caller's own config, is what does.

guards.ts also guards the plain transactions /trade/v1/swap hands back (assertSwapTransactions, step 8), called before ANY of them is sent: an approve tx's to must be the sell token (canonicalized the same way as the swap tx's tokenIn below, so a native-USDC sell token still matches the canonical USDC ERC-20 view an approve targets) and its calldata must decode to approve(spender, amount) with spender the ArcgateRouter address the caller configured, capped at the caller's max (approve mode), or Permit2, uncapped (permit2 mode). Exactly one swap tx is allowed: its to must be that same configured ArcgateRouter address, never a value read from the response, and its calldata must decode against ArcgateRouter's executeGraph ABI (any other selector is refused) to recipient and tokenOut matching this run's own recipient/buy-token config, amountIn within the caller's max, and minOut both positive and no looser than the floor (best.minAmountOut) the caller accepted at quote time (SwapTransactionsContext.minOut); its value must be 0 unless the caller allowed a native-USDC-funded swap, in which case it must equal the decoded amountIn scaled to 18dp exactly (packages/wallets/src/guards.ts's NATIVE_USDC_SCALE). A buggy or compromised server returning approve(attacker, MAX), a swap to somewhere other than ArcgateRouter, or a swap whose TOP-LEVEL recipient/tokenIn/amountIn/tokenOut/minOut don't match, is refused here, before this example's fork/Circle executors ever send it. This does not decode executeGraph()'s steps, pull, or deadline: a malicious server could still route the input badly inside steps while every top-level field above stays honest. That loss is bounded, not eliminated - ArcgateRouter only ever pays the checked recipient at least the checked minOut (_payGraphOutput, contracts/src/ArcgateRouter.sol), so the worst case is the same slippage the caller already accepted at quote time. A server that lies consistently in both the quote and the swap is a bad-price problem no wallet-side structural check catches without an independent price source.

5Search

cirBTC is a shared ticker: all four other hits above are lookalikes at other addresses, each flagged impersonates_canonical. Taking the first same-symbol hit would buy one of those impostors just as easily as the real token - the problem arcgate's search resolution exists to solve. Each result carries a verification.status and a flags array (see the API reference for the full SearchResponse schema); the top-level resolution (verified/clear_leader/single/ ambiguous/none) says whether the query resolved to a safe pick at all. pickSearchResult (packages/wallets/src/trade.ts) refuses on an ambiguous or unresolved resolution, and refuses the top result if it's flagged as an impersonator, a lookalike, or unsellable, or if its safety verdict is still pending (safety_pending). Here resolution is verified and the top result carries no such flag, so it picks 0x171a4217…, the real cirBTC.

6Quote

A quote is side: "exactIn" (sell an exact amount of USDC, get at least minAmountOut) or exactOut (buy an exact amount, pay at most a cap). It lives for ttlSec (default and max 120s); /trade/v1/swap re-quotes and re-simulates at the current block on every call regardless, so a shorter ttlSec only bounds staleness risk, not price risk.

route names the venue the price came from (uniswap_v3 here) - that's where liquidity is priced from, not who the swap transaction talks to on chain: this quote's swap still executes through arcgate's own router (see step 7).

7Swap

approval picks how the taker's allowance gets set:

  • permit2 (default, two calls). Every quote executes through ArcgateRouter, the swap's spender. If the route is funded with native USDC, or an existing Permit2 allowance to ArcgateRouter already covers the amount, the response comes back with signatures: [] - there is nothing to sign. Otherwise round 1 returns a Permit2 PermitSingle to sign (signatures[0].typedData) and a swap transaction built with an empty Permit2 signature (only directly sendable as-is when an allowance already exists). Sign it, call again with permit: { message, signature }; the response embeds the permit and clamps the on-chain deadline to min(now + deadlineSec, sigDeadline, expiration). This is the flow a real Circle mainnet wallet uses (step 8).
  • approve (one call). Returns a plain ERC-20 approve transaction instead. This example's local fork executor uses this, because impersonation (step 8) produces no signature to attach a permit to.

8Sign and broadcast

This is where the chain split in What you'll build matters. Circle's API was probed live with an ARC-TESTNET EOA wallet:

  • signTransaction (raw or JSON) is refused outright for an ARC-TESTNET wallet, at any target chain id: "the specified blockchain is either not supported or deprecated".
  • signTypedData works, but only when the payload's domain.chainId matches the wallet's own chain (5042002); it refuses 5042.

So an ARC-TESTNET wallet can pay x402 (step 4, signTypedData on its own chain) but cannot sign a mainnet (5042) swap transaction or Permit2 permit. Production execution needs a second Circle wallet, on blockchain ARC (mainnet), in its own LIVE-key wallet set (see Going to production), and a different Circle call: createContractExecutionTransaction - Circle signs AND broadcasts the transaction itself, on the wallet's own chain. This repo's code calls it sendWithCircle (packages/wallets/src/circle.ts):

idempotencyKey is deterministic (idempotencyKeyFor in packages/wallets/src/circle.ts, keyed on quoteId + transaction index + purpose): a retry of the same send within one run reuses the same key instead of double-sending. A fresh run gets a new quoteId, and so a new key - this does not make a re-run of the whole example idempotent, only a client-side retry within one.

This mechanic was verified live: a harmless approve(self, 0) through createContractExecutionTransaction on ARC-TESTNET reached COMPLETE, tx 0xe923da9991872d5b91007e1139d1fc61e0ed8bff83171991f2f44f86deaba413.

That confirms Circle's send-and-broadcast mechanic works; it does not change the chain-id refusal above, because the transaction it sent targeted the wallet's own chain (testnet), not 5042.

The production (circle executor) two-call Permit2 flow signs the permit before sending any approve transaction, executeWithCircle (examples/circle-trade/src/execute.ts):

txCtx runs assertSwapTransactions (see step 4) before ANY send: both first.transactions up front, and, after resign() returns a second server response, that response's own transactions too - a fresh response each time, checked each time.

ARCGATE_EXECUTOR=circle needs a live mainnet key and mainnet funds, so it does not run against this repo's localnet; it typechecks and is written directly against the SwapRequest/ SwapResponse schema in docs/openapi.json.

Locally (ARCGATE_EXECUTOR=fork, the default), the fork executor stands in (packages/wallets/src/fork.ts, shared with the other tutorial's example): it funds the wallet's address on the arc-anvil fork with anvil_setBalance, impersonates it with anvil_impersonateAccount, and sends each transaction with eth_sendTransaction from that address, waiting for every receipt - approves included - and refusing on any revert before moving on. This is never signing - anvil_impersonateAccount only works on a local test chain that will execute a transaction from any address it's told to impersonate.

When things go wrong

Run pnpm --filter @arcgate/example-circle-trade start -- --failures (same port overrides as step 3 if you're on a non-default localnet) for two of these live and a written explanation of the third.

Expired quote (410). Swapping past expiresAt never charges - no PAYMENT-RESPONSE header, so settlement is null:

402 loop from an unfunded wallet. A wallet with no testnet USDC signs a valid payment payload, but the facilitator refuses to settle it - the client gets a second 402 instead of a 200:

Warning

/trade/v1/swap re-simulates and re-quotes at the current block on every call. A slippage-shaped revert (the TooLittleReceived family - the market moved past minAmountOut) comes back 409 quote_stale, not a silent bad fill; every other executed revert is 422 swap_reverts instead.

Slippage revert. Not faked here - it needs a real price move between quote and execution. What it looks like: the swap transaction's receipt reverts on chain, even though /trade/v1/swap's own re-simulation passed. The fork executor (packages/wallets/src/fork.ts's waitForForkReceipt) already throws on any reverted receipt instead of reporting a delivery; the fix is to re-quote and swap again, never to relax minAmountOut.

Guard refusals. A refusing to sign error from assertX402Authorization or assertPermit2TypedData means the payload asked for something outside what this wallet is allowed to sign - the wrong chain, the wrong contract, a mismatched spender/token/amount, a deadline too far out. A refusing to send error from assertSwapTransactions means a plain transaction asked for something outside what this run is allowed to send - the wrong approve spender, an approve on the wrong token, an amount over what this run chose to sell, a swap to somewhere other than the configured ArcgateRouter, or a value this run didn't allow. These are refusals by design, not bugs to work around.

Going to production

ARCGATE_EXECUTOR=circle needs a second, separate Circle setup - not just a second wallet in the same set as the payer, since a Circle TEST key can never reach Arc mainnet:

  1. A LIVE Circle API key (LIVE_API_KEY:...) and its own entity secret, generated and registered the same way as step 1, from a separate Circle project/account suitable for holding real funds.

  2. A wallet set and one EOA wallet on blockchain ARC (mainnet) under that LIVE key - this is the swap wallet: it signs the Permit2 permit and sends every swap transaction, and it is the taker/recipient arcgate's swap targets, not the testnet payer. Production, not run here:

    (createWalletSet/createWallets option names checked against @circle-fin/developer-controlled-wallets's own type declarations.)

  3. An Arc mainnet RPC url, to check delivery after the swap the same way step 9 does locally.

  4. The real deployment address of ArcgateRouter on Arc mainnet. ARCGATE_ROUTER_ADDRESS is required for ARCGATE_EXECUTOR=circle - this example refuses to fall back to the localnet compose.yaml address here, since that address means nothing on the real chain.

Never log this

CIRCLE_SWAP_API_KEY and CIRCLE_SWAP_ENTITY_SECRET can sign for a wallet holding real funds on Arc mainnet. Treat them with more care than the testnet credentials above, not less.

Preflight also changes: production makes four paid calls, not three (search, quote, the first swap call, and the round-2 paid re-sign with the permit attached), so the balance check requires ARCGATE_MAX_PAYMENT * 4 instead of * 3.
