Trade through arcgate with MetaMask Agent Wallet

Use Claude Code with the MetaMask skills and mm 7.0.0 to pay x402 on Arc testnet, then search, quote, sign Permit2, decode, and send an Arc mainnet swap.

This tutorial uses @metamask/agent-wallet@7.0.0, the mm CLI, and MetaMask/agent-skills in Claude Code. The internal proof runner lives in examples/metamask-agent-trade/. Run end to end on September 28, 2026: four real testnet payments, a real MetaMask Permit2 signature, and a successful localnet swap. Delivery was 1,193 atomic units of cirBTC against a floor of 1,181.

Note

The localnet proof uses real mm signatures for testnet x402 payments and the mainnet-chain Permit2 permit. Transactions are broadcast by impersonating that address only on the fork. Real mm wallet send-transaction on mainnet is a separate launch check in #64, after ArcgateRouter is deployed. That check has not been run here.

What you'll build

An agent pays for each search, quote, and swap API call with an EIP-3009 USDC TransferWithAuthorization signed by mm wallet sign-typed-data. It chooses the intended token, accepts a quote, requests /trade/v1/swap, signs its Permit2 PermitSingle with the same command, and reviews the returned transactions with mm decode. Localnet broadcasts them by impersonation; the mainnet launch check uses mm wallet send-transaction.

Like the Circle tutorial, this flow separates two chains:

Purpose CLI network key Chain ID Where this tutorial executes
x402 payment arc-testnet 5042002 Real Arc testnet, testnet USDC
Quote and swap execution arc 5042 pnpm localnet's arc-anvil fork of Arc mainnet

mm takes numeric IDs in --chain-id. The keys above identify the entries in mm chains list. Unlike Circle's chain-specific wallet setup, this tutorial assumes one EVM server wallet address for both signatures. It does not export a key. Only transaction broadcasting on the local fork impersonates that address; both typed-data signatures are produced by the real MetaMask wallet.

The example trades 1 USDC for cirBTC, with 100 bps slippage and venues: ["uniswap_v3"]. That venue restriction makes this an ERC-20 input route: an entirely native-funded route would need no Permit2 signature. An existing sufficient Permit2 allowance also skips the signature. The proof runner stops in either case; that run would not demonstrate the requested signing flow.

Before you start

Use Node 24, pnpm, Docker, and Claude Code. Install the pinned CLI separately from the skills:

Start a new Claude Code session so the MetaMask skill is loaded. The skill provides signing, wallet policy, decode, and x402 guidance; it does not install mm or an arcgate client. These instructions were checked against agent-skills commit 9909fa4.

For this repository's proof run, install dependencies and set the root .env before localnet:

API_URL defaults to http://127.0.0.1:19800; ARC_FORK_URL defaults to http://127.0.0.1:19845. These variables configure the example, not MetaMask's broadcaster. The facilitator must list exact on eip155:5042002 in its /supported response. Allow 0.04 testnet USDC for four paid calls: search 0.005, quote 0.01, and two swap calls at 0.01 each for this trade size. See prices. Quotes expire after 120 seconds.

Why the swap executes on localnet

The published 7.0.0 CLI has no per-command RPC override for wallet send-transaction. Its wallet stack submits a transaction job to MetaMask's service in both modes: BYOK signs locally, then submits the signed transaction to the service. ARC_FORK_URL does not redirect that broadcaster. The fork shares chain ID 5042 with mainnet, but has separate state.

Following the Circle tutorial's localnet approach, this example funds the MetaMask address on the fork and broadcasts with anvil_impersonateAccount plus eth_sendTransaction. It still uses real mm wallet sign-typed-data for both the x402 authorization and Permit2 permit. Impersonation cannot produce the Permit2 signature: the router verifies the real signature when the fork executes the swap.

Arc testnet is only the payment chain here. As mvp.md explains, it has only the v4 venues, thin test-token liquidity, and none of this trade's tokens. A testnet trading environment would need its own venue config, indexed database, and ArcgateRouter deployment; it is outside launch scope. Real MetaMask transaction broadcasting is exercised by the small mainnet trade in #64, after the production router is deployed.

Check readiness first:

If unauthenticated, run mm login and complete its login flow. If uninitialized, this tutorial chooses the hosted server wallet with policy enforcement:

On the checked machine, initialization already existed and was not rerun. mm init show reported:

The address was 0x72e17261e04e6162a62f034d8d71053ea37d35a3. Use your own selected address. BYOK (mm init --wallet byok) is a different custody choice; it is not this tutorial's assumption and does not solve the broadcast prerequisite. In BYOK, mm wallet policy get returns WRONG_WALLET_MODE rather than a server-wallet policy.

Never log this

Keep MetaMask login tokens, recovery material, mnemonics, and passwords out of source control and command output. This example needs none of them in application code. If you separately use an encrypted BYOK wallet, follow the MetaMask skill's MM_PASSWORD guidance; never pass a mnemonic or password in inline command arguments.

Confirm Arc availability

Arc support is gated by NetworkRegistry, which obtains server-supported networks; a locally known chain constant is insufficient. Check the active environment at run time. If either entry is missing, stop and resolve service support. relaySupported: false describes relay support; it is not evidence that signing or ordinary transaction submission is unavailable. Conversely, listing a chain is not evidence that the selected wallet's policy permits a transaction on it.

Inspect the server-wallet policy

The observed guard policy had an empty address allowlist and blocklist, omitted both 5042 and 5042002 from evm.allowed_chains, and set rolling_24h: 0. That policy does not provide unattended Arc trading authorization. A policy violation can require MFA or refusal; the fork broadcaster does not exercise MetaMask's send policy, so router/Permit2 acceptance still needs the real mainnet send in #64. Empty address lists alone do not prove an address-specific block. The real testnet x402 payments and the mainnet-chain Permit2 signature succeeded with this policy unchanged: do not assume a transaction outflow limit protects arbitrary typed-data signing.

For this flow, the ERC-20 approval transaction's destination is USDC and its calldata spender is Permit2. The swap transaction's destination and the Permit2 permit's spender are ArcgateRouter. There is normally no standalone transaction to Permit2: the router calls it. The template says shared address lists apply to direct destinations, Shield contract targets, and token recipients, so address policy review must cover all these roles.

Here is a proposed full policy, using the schema returned by the actual 7.0.0 template. Replace the wallet, payment recipient, and deployed router placeholders. It retains the template's required service-default chains, adds the two Arc chains, allows the deployed router and Permit2, and uses a finite $5 daily ceiling. Preserve any additional restrictions from your current policy when editing your own document.

For the mainnet launch check, review the complete document, then apply it through MetaMask. The localnet run leaves the live wallet policy unchanged:

Adding chains or addresses and raising the outflow limit are broadening changes that require MFA. Wait for approval of the existing job and confirm the resulting policy. Do not resubmit while it is pending or switch to beast to bypass a refusal. Shield and recipient risk checks are service-managed; YAML cannot disable them, and route-specific contracts may still trigger a review. This policy is not a promise that every route will be accepted.

4Pay x402 with the wallet (guards)

The unpaid HTTP call returns 402 and a base64 PAYMENT-REQUIRED header. The x402 client selects only exact, eip155:5042002, the testnet USDC contract, the configured PAY_TO, at most 10,000 atomic units (0.01 USDC), and a timeout at most 300 seconds.

createMetaMaskWallet().payer adapts mm to x402's ClientEvmSigner. It checks the TransferWithAuthorization domain, chain, contract, sender, and validity window before calling:

The authorization has from, to, value, validAfter, validBefore, and a fresh bytes32 nonce; it is EIP-3009, not Permit2. The CLI returns the signature under data.signature with status SIGNED. The adapter recovers the signer locally and refuses another address. The x402 SDK packages the signature and authorization into PAYMENT-SIGNATURE, then retries the identical API request once. It checks the returned PAYMENT-RESPONSE settlement before moving on. A second 402 is an error, not permission to sign again.

The same guarded payment happens separately for search, quote, swap round 1, and swap round 2. The CLI adapter passes argument arrays directly to the subprocess and never exports a key. The runner does not use the upstream x402 helper's default payment selection or chain assumptions.

5Search

BUY is 0x171a4217b86a807a64eb94757db6849fb4bdbaa0. A ticker alone does not identify the asset. The picker refuses an ambiguous resolution, impersonator, lookalike, unsellable token, or pending safety result, and requires the expected address.

6Quote

The API's execution chain is Arc mainnet (5042), locally forked. Paying the API on testnet does not change that. The runner binds the quote's sell/buy addresses and input amount to the order (sell.amount and sell.amountRaw for exactIn; best.amountIn is an exactOut field). It records quote.best.minAmountOut as the floor for every later calldata check and delivery check; a later swap response cannot quietly lower it. Quote lifetime is 120 seconds.

7Swap

For a fresh allowance on this ERC-20 route, round 1 returns a USDC approval to Permit2, a signatures[0].typedData Permit2 PermitSingle, and swap calldata with an empty permit signature. Do not send that placeholder swap. Review every transaction, then check the permit's domain (5042, Permit2), spender (the independently configured ArcgateRouter), token (USDC), amount (at most 1 USDC), and both deadlines.

8Sign and broadcast

Use mm decode on the swap calldata as well as the approval, before sending either:

The decoder is a guardrail, not an authorization oracle. The example reviews approve and executeGraph parameters, and independently decodes calldata with the local ArcgateRouter ABI to check destination, recipient, tokens, amount, native value, and the quote's minimum output. On the live CLI, an existing executeGraph calldata capture returned:

The public selector lookup did not know this router function. The localnet runner explicitly falls back to the repository's exact executeGraph ABI, prints its decoded fields, and requires all the structural checks above before broadcasting. An ABI decode failure or mismatched field still stops the run. The generic CLI adapter stops on unknown calldata unless that explicit fallback is selected; an unknown selector alone is never approval. The structural check does not independently price the route or inspect every nested venue call.

Sign the permit first, then send any approval and wait for its successful fork receipt. sendOnFork checks a loopback RPC and chain 5042, impersonates only the selected MetaMask address, calls eth_sendTransaction, checks the receipt, and stops impersonation in finally. This is a local broadcaster, not a MetaMask transaction signature.

Round 2 carries the original message and the signature from mm:

Review the new calldata again because round 2 re-quotes and re-simulates. Require no remaining signature request. Send the final returned transactions in order, waiting for each receipt. In the later mainnet CLI flow, data.hash with BROADCASTED or CONFIRMED identifies a submission; it does not replace receipt and delivery checks. A pollingId, AWAITING_MFA, denied job, or timeout is not success. Watch the existing request with mm wallet requests watch <pollingId>; never automatically resubmit a transaction after an uncertain result.

When things go wrong

  • Missing Arc entry: resolve NetworkRegistry/service support. Wallet policy cannot add an unsupported network to the service.
  • Policy refusal/MFA: inspect policy get and policy template, review the concrete request, and approve the existing job if intended. Confirm policy set actually completed.
  • Insufficient testnet USDC: fund the selected payer on 5042002; local fork funding cannot pay the API.
  • Unknown calldata: use the exact local ABI review described above before fork broadcasting. Stop if it cannot decode the function or any expected field differs.
  • No Permit2 signature: the route or current allowance skipped it. Use a fresh allowance state on localnet; do not claim a Permit2 signing run.
  • 410 quote_expired or 409 quote_stale: obtain a fresh quote and review its floor. MFA may outlast the 120-second quote. Do not automatically replay an approval or loosen slippage.
  • Reverted receipt: stop. /swap simulation is not a guarantee against later state changes.

Going to production

The real mm wallet send-transaction belongs to the small mainnet launch trade in #64, after ArcgateRouter is deployed. The localnet proof does not verify MetaMask's mainnet broadcast, Shield, or transaction policy acceptance. Before that check, use the actual deployed router address, fund the mainnet wallet with a tiny reviewed amount and gas, and confirm the policy change completed.

The production transaction command is:

transaction-hex.json contains one reviewed /swap transaction. The API's value and gas are decimal strings; convert them to hex (numberToHex(BigInt(tx.value)) and numberToHex(BigInt(tx.gas))) and keep only transaction fields. The CLI adapter's wallet.send implements this command; the localnet runner deliberately calls sendOnFork instead. Send approvals first, check each receipt, then send the final swap with the signed permit and check delivery. Record the real transaction hashes in #64 and the policy rejection/approval outcome. Do not substitute the localnet router address for an actual mainnet deployment.

Production arcgate can also charge x402 on mainnet; this tutorial's payer intentionally refuses that offer. The mainnet payment mode is separate work in #64: review its payment domain and hard fee cap rather than only changing the execution chain ID. No mainnet funds were spent here.
